# מטלה — הערות קצרות (ארכיטקטורה, AI, Code Review)

## Design Patterns

**בצד הלקוח (Angular, `edu-management`)**

- **Dependency Injection** — שירותים (`@Injectable`, `inject()`) מפרידים בין UI ללוגיקת גישה ל-API.
- **Service Layer** — שכבת שירותי HTTP לפי פיצ'ר (למשל `StudentsService`, `EducationPlacesService`) עם DTOs תואמי שרת.
- **Interceptor (של שרשרת HTTP)** — `apiBaseUrl` ו-`errorHandler` מרכזים cross-cutting (בסיס URL, מיפוי שגיאות, פידבק למשתמש) בלי לשכפל בכל קריאה.
- **Lazy loading** — נתיבים נטענים לפי מודול/פיצ'ר, לפישוט אתחול ולחלוקה לוגית.
- **State / Store מבוסס Signals** — ניהול מצב מרוכז (למשל `EducationPlacesStore`) עם `signal` / `computed`, בלי store כבד חיצוני — דפוס "מיכל מצב" מקומי לפיצ'ר.

**בצד השרת (לפי מבנה המונוריפו)**

- **שכבות (Layered / Clean Architecture)** — הפרדה בין API, Application, Domain, Infrastructure.
- **Repository** (גישה ל-SQL עם Dapper) — בידוד גישה לנתונים מהלוגיקה העסקית.

## שימוש ב-AI

**במטלה הנוכחית**

- כלי AI (למשל Cursor) שימשו ל**סריקת קוד**, **הצעות עקביות** עם המבנה הקיים (פיצ'רים, שירותים, מודלים), ו**זירוז איטרציות** על טפסים, דיאלוגים וטיפול בשגיאות — תוך שמירה על סקירה ידנית של חוזי API והתאמה ל-DTOs בפועל.

**כמוביל צוות — שילוב סוכני AI ו-Copilot בפיתוח ו-QA**

- **בפיתוח:** Copilot/סוכנים לדוגמאות קצרות, בדיקות יחידה ראשוניות, ותיעוד inline — עם **כללי ארגון** (לא להדביק קוד בלי קריאה, לא לסמוך על הצעות לחוזי API או סודות).
- **ב-PR:** תבנית PR קצרה + ביקורת אוטומטית (לינט, בנייה) + אופציה לסיכום שינויים/סיכונים בעזרת AI.
- **ב-QA:** יצירת **מטריצת תרחישים** (smoke + רגרסיה) עם עזרת AI, כתיבת צעדי שחזור, והדגשת בדיקות **קצה-לקצה** קריטיות שדורשות אימות אנושי.
- **Governance:** מדיניות ברורה — מה מותר להריץ אוטומטית ב-CI, ואיפה חובה אישור אדם (אבטחה, נתונים אישיים, שינוי חוזי API).

## חניכה — Code Review למודול "מורים"

אם מפתח ג'וניור מוסיף מודול **מורים**, בביקורת הייתי מדגיש:

1. **עקביות עם פיצ'ר קיים** — מבנה תיקיות דומה ל-`students` / `education-places`: רכיבי דף, שירות HTTP, מודלים תואמי ה-API, וללא לוגיקת דומיין "עבה" ברכיבים.
2. **חוזה API לפני UI** — לוודא DTOs, נתיבים וקודי שגיאה מול Swagger/OpenAPI; לא להמציא שדות.
3. **שימוש בתשתית** — אינטרספטורים, `ToastService` / פידבק מבצעים, ומיפוי שגיאות קיים — לא לבנות טיפול כפול.
4. **טפסים וולידציה** — שימוש בולידטורים מ-`core` או הרחבה עקבית; התאמה לכללי הבקאנד (אורך, פורמט, ייחודיות).
5. **מצב וריאקטיביות** — אם יש רשימה/סינון מורכב — לשקול store מבוסס Signals כמו בפנימיות; אם מסך פשוט — לא להכביד.
6. **נגישות ו-RTL** — טקסטים בעברית, כיוון ממשק, והתנהגות מקלדת/מסך קריא.
7. **בדיקות ובנייה** — לפחות בדיקת עשן או יחידה לשירות הקריטי; `ng build` נקי לפני מיזוג.
