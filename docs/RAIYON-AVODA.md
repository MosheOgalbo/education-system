# הצגת הפרויקט בראיון עבודה — החלטות ארכיטקטורה וקוד

מסמך זה מסכם **למה** נבחרו טכנולוגיות ודפוסים בפרויקט, ומה היו החלופות ומה הן עלויותיהן. אפשר להשתמש בו כתזכיר לראיון או כנקודת פתיחה לשיחה טכנית.

---

## תמצית מוצרית (30 שניות)

מערכת Full-Stack לניהול **פנימיות** ו**תלמידים** עם API עקבי, ולידציה עסקית בשרת, וממשק בעברית. הדגש: הפרדת שכבות, שגיאות JSON אחידות, וחוויית מפתח טובה (Swagger, Docker).

---

## Backend: .NET 10 + ASP.NET Core Web API

**למה:** מודל מוכח לארגונים ולצוותים בצורת C#, תיעוד רשמי חזק, ביצועים טובים ל-API, ותמיכה טבעית ב-DI, middleware ו-open metadata ל-Swagger.

**אלטרנטיבות:** Node (Express/Fastify) — מהיר לפרוטוטייפ, פחות תחושת «שכבות» טיפוסית בארגונים גדולים; Java Spring — דומה בעקרון, כבד יותר לפרויקט לימודי בגודל זה.

**מה בחרתי בפועל:** שכבות `API → Application → Domain → Infrastructure` כדי שהלוגיקה העסקית לא תיטמע בקונטרולרים ולא ב-SQL ישירות, וכדי לאפשר החלפת מאגר או בדיקות יחידה על שירותים.

---

## גישה לנתונים: Dapper ולא Entity Framework (בפרויקט זה)

**למה Dapper:** שליטה מלאה ב-SQL, פרוצדורות ואינדקסים; תוצאות ממופות במפורש ל-DTO — מתאים כשיש טבלאות ברורות ופרוצדורת אגרגציה (`sp_GetEducationPlacesWithStats`).

**מתי EF היה עדיף:** מודל דומיין עשיר עם מיגרציות אוטומטיות, יחסים רבים, ושינויי סכמה תכופים מתוך הקוד.

**מסר לראיון:** הבחירה היא **trade-off** — פחות «קסם ORM», יותר ביצועים צפויים ו-SQL נראה לעין בקוד הריפוזיטורי.

---

## SQL Server

**למה:** תאימות לסביבות ארגוניות רבות; Docker רשמי ל-SQL Server 2022; סקריפטי מיגרציה גלויים בתיקיית `database/migrations`.

**הערה על Docker:** תמונת `linux/amd64` — ב-Apple Silicon הרצה במוליך; זה **מודעות לסביבה** ולא באג.

---

## טיפול בשגיאות: Middleware גלובלי + חריגות דומיין

**למה לא `try/catch` בכל קונטרולר:** כפילות, סיכון לשכוח מיפוי קוד HTTP, וקושי לשנות פורמט JSON פעם אחת.

**למה `ValidationException` / `NotFoundException`:** המגייס רואה שאפשר למפות במפורש ל-400/404 ולהחזיר הודעה בעברית למשתמש, בלי לחשוף פרטים פנימיים ב-500.

**הרחבה (`ICriticalErrorNotifier`):** נקודת וו לעתיד (Sentry, מייל) בלי ללכלך את ה-middleware.

---

## Frontend מודרני: Angular 21 (standalone, lazy routes)

**למה Angular ולא React/Vue לפרויקט זה:** דגש על מבנה מודולרי, Router ו-DI מובנים, וחיבור טבעי ל-Material לטפסים וטבלאות; מתאים לתיאור «מערכת ארגונית» בראיון.

**למה `bootstrapApplication` + רכיבים standalone:** כיוון המודרני של Angular (פחות `NgModule` כבדים), טעינה עצלה פשוטה עם `loadChildren`.

**למה `PreloadAllModules`:** אחרי טעינה ראשונה, מודולים נטענים ברקע — איזון בין זמן first paint לבין ניווט חלק בין מסכים בפרויקט קטן-בינוני.

**למה `withViewTransitions`:** שיפור תחושת מעבר בין דפים בתמיכת דפדפן (כשזמין), בלי ספריית אנימציה נפרדת לכל מסך.

**למה `eventCoalescing` ב-Zone:** פחות מחזורי change detection על אירועי עכבר/מקלדת צפופים — רלוונטי לטבלאות וסינון.

---

## HTTP בצד Angular: Interceptors פונקציונליים

**מקדם כתובת (`apiBaseUrlInterceptor`):** כל השירותים קוראים לנתיב יחסי (`/api/...`); בסיס ה-URL מגיע מ-token אחד — קל להחליף סביבה (פיתוח עם proxy, פרודקשן עם אותו קוד).

**שגיאות (`errorHandlerInterceptor`):** מיפוי אחיד ל-`ApiError`; טוסט על פעולות שינוי ולא על כל GET — כדי שלא יופיעו **שתי** הודעות כשמסך כבר מציג מצב שגיאה מלא.

---

## AngularJS 1.x כלקוח נפרד

**למה קיים:** מממש דרישת Hands-On (legacy) במקביל לממשק המודרני — מראה הבנה של שני דורות ושל async/await מול `$http`.

---

## Docker Compose: סדר השירותים

**sqlserver → db-init → api → web:** אתחול סכמה רק אחרי בריאות SQL; ה-API רק אחרי שהמיגרציה הצליחה; ה-UI תלוי ב-API.

**פורטים:** ברירת מחדל API על **5001** ב-host כדי להימנע מקונפליקט עם שירותים על 5000 ב-macOS; משתני סביבה מתועדים להחלפה.

**`DISABLE_HTTPS_REDIRECT`:** בתוך קונטיינר לעיתים אין HTTPS termination — redirect היה שובר את הדפדפן.

---

## סקריפטים (`scripts/`)

**`compose-down.sh`:** לא רק `docker compose down` — אופציה להרוג תהליך `ng serve` על פורט כדי שלא יישאר מאזין אחרי ירידת הקונטיינרים.

## נקודות לדיבור בראיון (שאלות נפוצות)

| שאלה | כיוון תשובה קצר |
|------|------------------|
| למה לא מיקרוסרוויסים? | גודל צוות ופרויקט לא מצדיקים פיצול תפעולי; מונוליט מודולרי מהיר יותר לדמו. |
| איך מאבטחים API? | ולידציה בשרת, פרמטרים מקושחים ב-SQL (Dapper), CORS מוגבל; לא סומכים על הלקוח. |
| איך מתמודדים עם שגיאות בצד לקוח? | Interceptor מרכזי + מצבי UI ברכיבים ל-GET. |
| מה היית משפר בפרודקשן? | אימות (JWT/OIDC), ריטריי ל-HTTP, בדיקות אינטגרציה אוטומטיות, סודות מחוץ ל-compose. |
